## 1. FastAPI · 服务设计

### 1.1 技术栈

- Python 3.11 + FastAPI + Uvicorn；数据层 MVP 阶段用 SQLite（快照数据），预留 PostgreSQL。
- 所有业务系统数据均为**只读快照**（每日两次拉取，f34），服务不回写 OMS/WMS。

### 1.2 接口契约（核心 5 个）

```
GET /parcels/{parcel_id}/status
  → 返回节点时间线：signed_at / queued_at(null=黑箱) / inspected_at / refund_status
  → 若「签收后未排检」，返回 waiting_reason="queued_not_visible"（对应 f10 空窗）

GET /parcels/{parcel_id}/explain
  → 状态解释文本 + 依据条目（RAG 引用，带事实编号），供客服直接转述

POST /exceptions/{parcel_id}/claim?claimant=工单员
  → 一包多单/数量不符 → 待办认领：记录接手人与时间，状态 pending → claimed（f11、f23、f25）
  → 返回 {exception, sla_hint:null}   # sla 尚无统计，不编造

POST /exceptions/{parcel_id}/close?operator=工单员
  → 仅接手人可确认核对完成：claimed → closed，不自动关闭（f23）

GET /metrics/completion?caliber=cs|wh|fin&date=
  → 三口径完成量对照：10 500 / 9 847 / 9 402（f53），返回差异明细

GET /kb/ask?q=
  → 知识库问答（RAG + Wiki），回答必须带来源引用，无来源则回答"尚无记录"
```

### 1.3 数据模型（最小集）

- `parcel`（包裹号、售后单号[]、当前节点、各节点时间戳）
- `exception`（类型：一包多单/数量不符/资料缺失/版本冲突；状态：待核对/已认领/已关闭）
- `metric_snapshot`（日期、口径、完成量）
- `fact`（编号、文本、来源材料、角色）——与 `02_调研记录.json` 同构，直接导入。

## 2. Harness · 评测框架

### 2.1 评测集构建

以 35 条事实为金标准：每条事实生成 1–3 个问句（问状态、问卡点、问口径），答案要点 = 事实文本，来源 = 事实编号。产出 `eval_facts.jsonl`：

```json
{"id":"f10","q":"包裹 WB20xxxx 现在卡在哪？","expect":["签收后未排上质检","无系统状态"],"source":"f10"}
```

### 2.2 评测指标（与项目章程对齐）

| 指标 | 目标 | 证伪条件 |
| --- | --- | --- |
| 状态解释准确率 | ≥99%（f02） | <99% 即回到 O1 重排 |
| 引用可追溯率 | 100%（每条解释带 f 编号/材料名，f15 要求） | 任一解释无来源即不通过 |
| 幻觉率 | 0（无来源时必须答"尚无记录"，f34 待刷新口径） | 出现编造时长/编造状态即失败 |
| 分派正确率 | 100% 只派给工单员，不自动关闭（f25） | 误派/自动关闭即失败 |
| 红线违反 | 0（自动退款、欺诈认定、越权取数） | 任何一次即熔断下线（f41、f42） |

### 2.3 运行方式

`python -m harness.run --suite facts --threshold 0.99`；每次改 prompt/检索参数后必须全量回归；结果输出 `harness/report.json`（通过率、失败用例、失败原因分类）。

## 3. 知识库 · RAG + LLM Wiki（知识图谱）

### 3.1 RAG 语料（四来源）

1. `资料02_SOP_v3.2`（流程、时限、交接五要素）
2. `资料03_数据说明_v1.4`（字段口径、编号规则、多对多关系、刷新频率）
3. `资料04_周报_2026W44`（指标基线、三口径数据）
4. `02_调研记录.json` 的 35 条事实（切片最小单位 = 单条事实，天然带编号与角色）

切分策略：事实类整条入库（不切分）；制度类按条款切分；每片 metadata = `{source, version, date, fact_id?}`。

### 3.2 LLM Wiki（结构化词条）

| 词条 | 内容要点 | 引用 |
| --- | --- | --- |
| 签收后黑箱 | 签收→排检无系统状态、无时限、责任人待定 | f10、f01、f25 |
| 一包多单 | 定义、处理路径、无人认领现状 | f11、f15 |
| 三套完成口径 | 到仓/验收/到账，差异 1 098 件（10.5%） | f50、f53 |
| 交接确认规则 | 接手人确认接手才算转移 | f23 |
| 转人工四类触发 | 无法核对/缺依据/版本冲突/系统不可用 | f44 |
| 红线清单 | 只读、不自动退款、不认定欺诈、不绕权限 | f32、f41 |

### 3.3 知识图谱（最小三元组）

实体：**包裹、售后单、流程节点、角色岗位、异常类型、口径**。
核心关系：`包裹-包含→售后单`（多对多，f31）、`售后单-经过→节点`、`节点-责任岗→角色`（排检节点=待定）、`异常-分派给→工单员`、`口径-归属于→岗位`。
图谱直接服务两个高频问题：「这单现在谁负责」「三个口径为什么对不上」。

## 4. 权限 · 管理员（SaaS）+ 分层用户

| 角色 | 层级 | 能做什么 | 不能做什么 | 依据 |
| --- | --- | --- | --- | --- |
| SaaS 管理员 | 平台层 | 用户开通、岗位映射、数据源接入配置、审计日志查看 | 改业务数据、看具体包裹内容 | 最小权限原则 |
| 质检员 | 岗位层 | 看本岗待检队列、异常件提示 | 看退款金额、改判定 | f15、f41 |
| 工单员 | 岗位层 | 认领异常件、看核对清单、写核对结论（MVP 仅备注） | 替质检判定 | f11、f25 |
| 客服 | 岗位层 | 查状态解释（带依据）转述给客户 | 承诺具体到账时间（到账仅日期，f31） | f10、f34 |
| 风险专员 | 岗位层 | 看全部、接收版本冲突裁定 | 被 AI 代替决策（一票否决人工保留） | f04、f41 |

**红线即权限**：所有接口默认只读；写操作仅「异常认领」与「核对备注」两类；按账号授权、禁止借用（f41）；每次查询留审计日志（f45）。

## 8. 课堂协作任务 · Issue 与 PR

白板第六条要求去**别人的仓库**提交一个 Issue 和一个 PR（须用本人账号，体现协作痕迹），建议做法：

- **Issue（报问题）**：选定一个使用中的开源仓库，检查其 README 或 issue 模板，提交一个可复现、可验证的问题报告，格式：环境/复现步骤/期望 vs 实际/建议。可结合本课程主题，如给某 FastAPI 或 RAG 相关项目报一个文档与实际行为不符的问题。
- **PR（改内容）**：从改动成本最低、最易被合并的入手——修正 README 错别字/失效链接、补充安装步骤、给中文文档修一处翻译错误。流程：fork → 改一个文件 → commit 信息写清楚 → PR 描述里说明动机与验证方式。
- **留痕**：提交后把 Issue 链接与 PR 链接回填到本节，作为课堂评分证据。
